## 1. 音乐库自动更新（服务端 `server/services/libraryWatcher.mjs` · `server/api/events.mjs`）
- 监听：`fs.watch(音乐目录, { recursive: true })`（Windows / macOS 原生支持，Linux 需 Node ≥ 20）；
  不支持递归时自动改为"每个子目录一个 watcher"，每次重扫后同步目录集合；另有 **30 秒兜底轮询**
  （比对"路径 + 大小 + 修改时间"签名），网络盘/不发事件的文件系统或 watcher 出错也不会漏。
- 防抖 1.2 秒；处理前间隔 1.5 秒取两次签名，大小或修改时间仍在变的文件视为"复制中"；Windows 上再尝试只读打开
  （复制中的目标通常被独占）。复制中的文件本轮跳过（新文件暂不出现，旧文件保持原样），2 秒后再查直到稳定。
- 重扫是增量的：未变化的文件直接复用已解析结果，只解析新增/变化的文件。封面 URL 带 `?v=修改时间`，同名替换不吃旧缓存。
- 推送：SSE `GET /api/events`。`library` 事件带完整列表；`lyrics` 事件带 .lrc 有变化的曲目 id（正在显示的歌词会重新加载）；
  每次（重新）连接先发 `hello`（库版本号），版本不同前端就重新拉一次列表，断线期间的变化也不会丢。
- 前端：`engine.updateQueue()` 按 id 合并，保持当前曲目、预加载元素、随机模式的"下一首"，**不打断正在播放的歌**；
  正在播放的歌被删除时继续播完（服务端已缓冲的部分），留在列表原位，切到别的歌时才移除。歌单弹窗开着也会就地刷新。
- 实测（Linux，递归 + 强制逐目录两种模式）：新增、子目录、慢速复制（6 秒写完，只在写完后推送一次，时长正确）、
  .lrc 新增、删除，以及播放中加歌/删当前歌，均正常。Windows 走 Node 原生递归监听（ReadDirectoryChangesW），未能在 Windows 实机测。

## 2. 背景样式：高斯模糊 / 流体（`public/js/ui/fluidBackground.mjs`）
- 右上角「播放页布局」弹窗新增「背景：高斯模糊 / 流体」，记在 `local-player/bg/v1`。
- 流体：72×44 的小 canvas 上画 5 团封面取色（色相分桶 + 饱和度加权，压到深色范围）的径向渐变，沿李萨如曲线缓慢漂移（周期 23–41 秒），
  CSS 拉伸铺满全屏——双线性放大本身就是柔和的网格渐变，不用 blur 滤镜。约 30fps 重画（实测 28fps）；切歌颜色逐帧插值约 1.2 秒交叉过渡。
- 低开销：小画布 + 无滤镜；流体模式下底栏去掉 backdrop-filter（背景每帧都在变，毛玻璃会被迫每帧重算）。
- 页面隐藏 / 选了高斯模糊时停帧；系统"减少动态效果"时不漂移，只在换歌时把颜色过渡完就停（实测 1 秒内 0 次重画）。

## 3. 封面共享元素转场（`public/js/ui/miniLyrics.mjs`）
我们的界面没有"底栏小封面 + 单独播放页"，所以把转场用在**进入/退出迷你歌词条**：唱片中心的封面 ⇄ 迷你条的小封面，经典/分栏两种布局都适用。
- 封面飞行：圆形 ⇄ 圆角方形，带唱片此刻的转角（落回唱片时预估飞行结束时它转到的角度），只动 transform 与圆角。
- **没有用 View Transitions，而是 FLIP（Web Animations）**：View Transitions 进行中再触发只能跳到终点重开（skipTransition），
  做不到"半路折返"；FLIP 版本飞行中再点一次，会从封面此刻的位置/大小/角度/圆角平滑折返（逐帧采样验证连续）。
  其余界面（舞台、底栏、卡片）用 CSS 过渡交叉淡入，天然可随时反向。"减少动态效果"时不飞，直接淡入淡出。

## 5. 歌词高亮时间（`public/js/player/lyricClock.mjs`）
### 为什么以前高亮比歌声早
1. **换行提前 0.15 秒**：旧代码 `line.time <= currentTime + 0.15` 就切到下一行。
2. **逐字羽化在前面"抢跑"**：渐变从 `fill − 0.55em` 到 `fill + 0.55em`，填充位置之前半个多字就开始变亮；
   按估算逐字时长（每字约 0.3–0.6 秒）折算，约提前 0.15–0.3 秒。
3. **没扣输出延迟**：声音经 Web Audio 输出，`audio.currentTime` 是"交给音频图的位置"，真正从扬声器出来还要再等
   `AudioContext.baseLatency + outputLatency`（实测桌面 Chrome 约 43ms；安卓、蓝牙耳机更大，系统上报多少就补多少）。
三者叠加，高亮大约比歌声早 0.35–0.6 秒（蓝牙更多），与"高亮提前很多"的反馈一致。

### 现在
`歌词时间 = audio.currentTime − (baseLatency + outputLatency) − 0.1s − 用户偏移 + [offset:]`
- 换行不再提前；羽化改为在填充位置**之后**拖尾（`fill − 0.8em → fill`），填充位置之前一个字也不提前点亮；
  唱完最后一个字后填充按原速度再走一个羽化宽度，让末字也完全点亮。
- **默认延后 0.1 秒**的依据：ITU-R BT.1359 —— 声音领先画面约 45ms 开始能察觉、90ms 以内仍可接受。
  0.1 秒让"歌在前"能感觉到，又基本在可接受范围的边上；再加上拖尾羽化，视觉上的"亮边"本身还会再晚一点，所以没有取更大值，避免割裂。
- 用户偏移：歌词区右下角 `− 歌词 +0.3s +`，每次 0.1 秒（按住连续调），点数值重置；正数 = 歌词延后（歌更靠前）。
  全局记住（`local-player/lyric-offset/v1`），对经典/分栏/迷你歌词条都生效；调整时暂停状态下也立即重新定位。
- `.lrc` 里的 `[offset:+/-毫秒]` 按 LRC 约定生效（正数让歌词更早），按歌曲单独作用。
- 「从这句播放」时，音频定位到与这句对齐的位置（反算时钟），不会先显示上一句再跳回。
- 已知局限：系统上报的输出延迟本身可能不准（尤其部分蓝牙设备），这正是保留手动微调的原因；估算逐字时长（没有逐字时间标签的歌词）也只是近似。
