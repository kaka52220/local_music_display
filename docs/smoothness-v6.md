# v6 流畅度：对比录屏分析 + 改动

## 录屏分析（/workspace/vids/netease2.mp4 vs ours2.mp4，两段都有 48kHz 单声道音轨）

**音量包络**（2ms 窗 RMS，`screenshots/v6/netease-vs-ours-audio-envelope.png`）：
- 网易云暂停 / 定位前的收尾：从正常电平降到 -60dB 大约用 **20–35ms**，是很短的防爆音淡出，不是几百毫秒的长淡出。
  起播淡入约 **10–20ms**。定位时静音间隙 **154–180ms**。
- 我们（旧版）：暂停是"一步到位"的硬切（一个 2ms 窗内从 -15dB 掉到 -52dB），起播约 6ms。定位间隙 224ms。

**点击 → 声音变化的延迟**（用播放键区域像素变化当作"点击生效"时刻，再和音轨边沿对比；两者都含录屏自身的音画偏移）：
- 网易云：**100–230ms**（7 次）
- 我们：暂停 **520–940ms**，继续 **630–1200ms**（9 次）

也就是说，在平板 Chrome 上点击后图标、唱臂立刻变了，声音却要再过 0.5–1 秒才停或才响，
而且是硬切。"突兀、不跟手"的感觉主要来自这里。原因推测：安卓 Chrome 的 `<audio>` 原生输出走大缓冲的媒体通路；
Web Audio（`latencyHint: 'interactive'`）走低延迟通路。

**"暂停时唱臂没抬起"**：逐帧核对 ours2.mp4，界面一进入暂停（▶ 图标），唱臂就抬起了（22.9s、23.6s、28–29s 等）。
00:00–00:01.5 这一段，点击发生在约 0.1s，从 0.2s 起已经是"播放中"（⏸ 图标）、唱臂落下，但音轨要到 1.49s 才有声。
00:16 是一次拖动定位，状态也是播放中。所以看到的"暂停却落臂"，其实是**声音比界面晚了将近 1 秒**造成的错觉，
不是唱臂状态的 bug。唱臂逻辑（意图 && (出声 || 切歌宽限)）在两种布局下的测试都通过。

## 改动
1. **声音包络（engine.mjs）**
   - 优先走 Web Audio：MediaElementSource → GainNode → master。AudioContext 在第一次 pointerdown/keydown 时创建或恢复。
   - 否则退回逐帧改 element.volume；iOS 忽略 volume，这时不做淡变。可以用 `?webaudio=0`，或在 localStorage 写 `local-player/webaudio=0` 强制关闭 Web Audio。
   - 时长：暂停淡出 280ms 后才真正 pause；继续时从 0 淡入 360ms（从真正出声的 playing 时刻算起）；
     定位先压低 120ms，seek 后等 seeked 再淡入 200ms；切歌时旧曲在另一个元素上淡出 180ms、新曲淡入 260ms。
     增益按电平的平方变化，用 15ms 一段的折线排进 AudioParam 自动化。
   - 快速连点：每个元素只保留一条包络，新淡变从当前实际电平接着走。被取代的淡变不会执行"随后暂停"这类后续动作。
     例如暂停淡出过程中点继续，声音会平滑拉回，元素一直没有被暂停。
   - 界面（图标、唱臂、唱片减速）都在点击当帧响应，只有声音做包络。
2. **唱片转速**：不再切换 animation-play-state，改为 rAF 逐帧推进角度，角速度带缓动：加速 520ms（ease-in-out），减速 820ms（ease-out）。
   被打断时从当前角速度接着走；每张唱片保留自己的角度。
3. **播放/暂停图标**：两个图标叠放，切换时交叉淡变，并带缩放和旋转（约 200–240ms）。
4. **歌词滚动**：容器不再用原生滚动，内层用 translate3d 位移。
   换行或定位后以 450ms ease-out 补间滚到新行。滚轮和拖动 1:1 跟手，松手带惯性，越界有阻尼，停稳后吸附到焦点线。
   高亮的颜色和缩放在 300ms 内过渡，各行字重统一（字重不可插值，切换时会"跳一下"）。
5. **进度条**：按下或拖动时拇指放大到 1.5 倍。
6. **缓存**：index.html 里的 CSS 和入口 JS 地址都带上 `?v=构建号`（public 下所有文件的路径、大小、修改时间的哈希）。
   index 本身和其余模块用 no-cache + ETag 协商，git pull 后平板不会再跑旧代码。

## 测量（headless Chrome，`/workspace/shot/v6.mjs`，曲线图见 screenshots/v6/curves-*.png）
曲线以"开始派发点击"为 0，Playwright 的点击本身约有 60–90ms 延迟。
- 暂停：增益 1 → 0 约 280ms，之后元素 paused；唱臂从 -4° 回到 -31° 约 400ms；角速度 1 → 0 约 820ms。
- 继续：增益 0 → 1 约 360ms；唱臂落下；角速度 0 → 1 约 520ms（唱臂落到一半时开始加速）。
- 定位：增益约 120ms 降到 0，seek，约 200ms 淡回；歌词位移约 450ms 补间到新行（ease-out）。
- 暂停淡出过程中（约 150ms）点继续：增益最低降到约 0.08 后拉回 1，元素没有被暂停。

## 后续可以考虑
- 网易云当前行是**逐字高亮**（卡拉 OK 式，一行内从左到右变白）。如果有逐字时间轴（或者按行时长估算），
  我们也能用渐变遮罩实现，会进一步提升"跟着唱"的流动感。
