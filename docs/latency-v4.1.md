# v4.1 操作响应延迟：测量与修复

用户反馈：拖进度、切歌、暂停/播放总是慢 0.几秒。网易云进度条上有"缓存到哪里"的浅色段，我们没有。
缓存段本身不会造成延迟（已补上），真正的原因如下。

## 测量方法
- headless Chrome（playwright）注入脚本：在 `pointerdown` 记时，逐帧检查界面状态（播放图标、唱臂、标题、进度条、时间文字）
  和音频状态（`playing/pause/seeked` 事件、`currentTime` 是否在走）。每项取 3 次中位数。
- "Wi-Fi" 场景：本机限速代理 2.5 MB/s（≈20 Mbit，平板经局域网访问电脑）；另用 60 KB/s / 400 KB/s 复现慢网。
- curl 检查音频接口响应头。

## 原因（按影响排序）
1. **MP3 里内嵌的封面图让 Chrome 起播很慢。** 这几首 MP3 开头的 ID3 标签里塞着 57–543 KB 的封面；
   Chrome 遇到内嵌封面时要先下载完整个标签、再多读约 1 MB 才报 `loadedmetadata`。
   400 KB/s 下首次出声 3.8 s，去掉标签后 0.1 s；2.5 MB/s 下每次切到没缓冲过的歌要多等约 0.4–0.5 s。
   → 服务器播放接口跳过 ID3v2 标签直接从音频帧开始发（封面和歌名本来就由 `/api/cover`、`/api/tracks` 单独提供）。
2. **切歌每次都换 src 从头下载。** 没有预加载，下一首/上一首都要重新请求。
   → 引擎增加预加载池：当前曲目已出声且缓冲领先足够后，用隐藏的 Audio（preload=auto）预先加载下一首和上一首，
   切歌时直接把已缓冲好的元素换上来（切歌后网络请求数 = 0）。主元素也改为 preload=auto。
3. **切歌后标题延迟 200 ms 才换。** 之前为了"先淡出再换字"用了 setTimeout(180/200ms)。
   → 当帧换字 + 0.3 s 淡入动画。歌单点歌之前也会先等 200 ms 再切，现在立即切。
4. **进度条/时间/歌词跟着原生 `timeupdate` 走（约 250 ms 一次）。** 起播后进度条要 ~270 ms 才动，拖动松手后歌词高亮最多晚 250 ms。
   → 播放中用 requestAnimationFrame 逐帧读取 `currentTime` 派发进度（只在数值变化时写 DOM）；
   进度条精度 1000 → 10000 步；定位后立刻按目标时间回报（不等 `seeked`），拇指不回跳；支持 fastSeek 的浏览器松手时用 fastSeek。
5. **服务器没有缓存头。** 音频接口加 ETag / Last-Modified / Cache-Control（max-age=1 天）、304、If-Range、"bytes=-N" 后缀区间、HEAD；
   页面资源加 ETag + no-cache（改代码立即生效，没改则 304）。服务器本身很快（首字节 ~1 ms，不逐请求解析元数据）。
6. 检查过、不是原因的：没有暂停/播放淡入淡出（暂停立即生效）；播放图标与唱臂已是乐观更新（点击当帧）；
   进度条拖动中拇指本来就跟手，只在松手时定位。

## 缓存段
进度条（两种布局）新增三段绘制：已播放 / 已缓存（浅色半透明）/ 未加载，数据来自 `audio.buffered`（取包含当前位置的区间），
在 progress / seeked / 切歌时更新。截图：`screenshots/v4/buffered-split-bar.png`、`buffered-classic-bar.png`。
